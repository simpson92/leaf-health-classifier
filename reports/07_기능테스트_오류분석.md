# 산출물 7. 기능 테스트 및 오류 분석

테스트는 두 종류로 나눠서 기록한다. 둘을 같은 "실환경 PASS"로 섞지 않는다.

| 구분 | 방법 | 검증 범위 |
|---|---|---|
| **모의 테스트** | `python -m pytest -q` ([`tests/test_api.py`](../tests/test_api.py)) | 가짜 모델·SQLite·가짜 Redis로 HTTP 응답과 상태 변화만 확인 |
| **실환경 통합 테스트** | 실제 서버·Worker·Docker로 직접 실행 | 실제 ResNet18, Redis, Celery, PostgreSQL 연결 |

## 3. 오류·특이 사항 기록

| ID | 현상 | 원인 | 조치 | 재검증 |
|---|---|---|---|---|
| E-01 | `pytest`에서 `/static/style.css` 404 | `static/` 폴더에 `style.css`가 없었음 | 파일 생성·저장 | `pytest` 통과 |
| E-02 | `python -m training.check_data` 실행 시 모듈을 찾지 못함 | 데이터 폴더(`~/beans_source`)에서 실행 | 프로젝트 루트로 이동 후 실행 | 정상 실행 |
| E-03 | Redis 재시작 직후 작업의 큐 대기 6.0초 (평소 약 5ms) | Worker가 끊긴 Broker 연결을 감지하고 재연결하는 시간 | 조치 불필요. 장애 복구 후 정상화까지 약 6초로 기록 | 이후 작업 정상 |
| E-04 | 동시 20건에서 비동기 접수가 260ms로 느려짐 | 연결 풀 부족 가설 → 실험으로 **기각** | 기본값 유지, 프로세스 수를 다음 후보로 기록 | [산출물 6 §7](06_성능비교_보고서.md) |
| 참고 | 학습·서빙 시 `use_fast`, `not initialized` 경고 | 이미지 처리기 안내, 1000→3클래스 출력층 새로 생성 | 오류 아님 | - |

## 4. 오분류 분석

**Test 유일한 오분류 (최종 모델 E3)**

| 파일 | 정답 | 예측 | 확신도 | baseline 예측 |
|---|---|---|---:|---|
| `bean_rust_test.15.jpg` | 녹병 | 반점병 | 0.6047 | 반점병 (0.5265) |

baseline도 같은 실수를 한 이미지다. 녹병과 각진잎반점병은 둘 다 잎에 작은 반점이 생겨 모양이 비슷하다. 실제로 baseline의 Test 오분류 36건 중 20건이 두 병 사이의 혼동이었다 ([`eval_test_wrong.csv`](data/models/beans_resnet18/eval_test_wrong.csv)).

**정답이지만 확신도가 낮았던 사례**

| 이미지 | 예측 (정답) | 확신도 | 출처 |
|---|---|---:|---|
| `bean_rust_test.36.jpg` | 녹병 | 53.6% | job 127 |
| `bean_rust_test.11.jpg` | 녹병 | 64.3% | ![](evidence/sync_miss.png) |

유일한 오분류의 확신도(60.5%)가 이 범위와 겹친다. **확신도가 낮은 결과를 자동 확정하지 않고 "확인 필요"로 분류**하는 방식이 다음 개선 후보다(미구현, [산출물 8](08_최종기술보고서.md) §8).
